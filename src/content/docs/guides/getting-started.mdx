## Start with the source repositories

Conxian.org is a documentation surface, not a hosted gateway or custody service. Begin with the [Repository Status Matrix](/ecosystem/status/) and open the repository that matches your task.

- [`conxian-gateway`](https://github.com/Conxian/conxian-gateway) — institutional integration and compliance middleware.
- [`conxian-nexus`](https://github.com/Conxian/conxian-nexus) — state, proof, synchronization, and telemetry infrastructure.
- [`conxius-enclave-sdk`](https://github.com/Conxian/conxius-enclave-sdk) — enclave, signing, and attestation abstractions.
- [`conxius-platform`](https://github.com/Conxian/conxius-platform) — local stack composition and developer orchestration.
- [`lib-conxian-core`](https://github.com/Conxian/lib-conxian-core) — shared serialization, cryptographic, and state primitives.
- [`conxius-wallet`](https://github.com/Conxian/conxius-wallet) — offline-first wallet and signing client with user-controlled keys.

## Evaluate claims conservatively

Before integrating a capability, check the repository README, release evidence, tests, and the maturity/claim-state row in the portfolio doctrine. `Implemented` means code or configuration exists; it does not by itself mean verified production readiness. `Target-state` means intended architecture or roadmap.

## Boundary rules

Conxian-Labs is a non-custodial builder/operator. Users retain control of wallet keys, while protocol or DAO state follows contract- or governance-defined rules. Do not send secrets, regulated data, or production credentials to this documentation site.

For corporate, legal, or business operations, use the appropriate Conxian-Labs surface rather than treating this developer portal as an operations console.
